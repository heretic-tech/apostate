# Build pins

The build contract is target-specific and reproducible. For a target, the
effective tuple

```text
(CHROMIUM_VERSION, DEPOT_TOOLS_REVISION, args/<target>.gn,
 linux/Dockerfile when applicable, patches/series)
```

fully determines the output binary. Changing any input changes what ships, so
each input is pinned in the repository rather than treated as a convention.

`CHROMIUM_VERSION` is `152.0.7977.83`, recorded in
[`build/CHROMIUM_VERSION`](CHROMIUM_VERSION). The package and artifact
contracts use this exact version.

## Target definitions

`build/args/<target>.gn` is the complete effective GN configuration for one
release target. It is not a generic host hint: target OS, CPU, SDK/toolchain,
linker, sysroot or container boundary, and reproducibility settings belong in
the target definition. A target must not inherit Linux container assumptions
when it is macOS or Windows.

The initial target and artifact names are:

| Target | Definition | Artifact |
| --- | --- | --- |
| `linux-x64` | `build/args/linux-x64.gn` | `apostate-152.0.7977.83-linux-x64.tar.zst` |
| `linux-arm64` | `build/args/linux-arm64.gn` | `apostate-152.0.7977.83-linux-arm64.tar.zst` |
| `macos-arm64` | `build/args/macos-arm64.gn` | `apostate-152.0.7977.83-macos-arm64.zip` |
| `windows-x64` | `build/args/windows-x64.gn` | `apostate-152.0.7977.83-windows-x64.zip` |

Linux targets use the pinned `build/linux/Dockerfile` boundary where the build
workflow requires it. macOS runs against the pinned SDK/toolchain settings in
its target definition. Windows requires its own explicit SDK, toolchain,
packaging, and reproducibility settings; it is not a Linux-container variant.

All four target definitions build. `linux-arm64` is cross-compiled from the
x64 runner inside the pinned container, because that container is the
reproducibility boundary and `scripts/in-linux-build-container.sh` requires a
Linux x86_64 host. `windows-x64` builds natively; its definition pins no
toolchain path, because `scripts/lib.sh` exports `DEPOT_TOOLS_WIN_TOOLCHAIN=0`
and `vs_toolchain.py` resolves Visual Studio, the Windows SDK and the CRT
runtime directories from the runner's own installation as one consistent set.

## Resolved manifest

`MANIFEST.lock` is generated by `scripts/build.sh` and records what a build
actually resolved: the target, Chromium revision, depot_tools revision,
patch-series and patch-contents hashes, the GN-argument hash, toolchain or
image information, build lineage, and output hashes. The checked-in file is
evidence of its recorded target only; it is not evidence for targets that were
not built.

`scripts/validate-release-baseline.py` checks it, and the release gate runs
that check with `--release` on the tagged revision **before** any build
starts. Because `patch_contents_sha256` hashes every patch's bytes, changing
any patch moves it and the gate fails until it is refreshed. The refresh
needs no build -- both digests are functions of the patch files -- so
`scripts/validate-release-baseline.py --refresh` rewrites those two fields
and leaves the rest of the build record alone. Without `--release` the same
check reports the drift as a notice and exits zero, because between builds
the digests are expected to be behind.

See [`docs/contributing/releases.mdx`](../docs/contributing/releases.mdx) for artifact names, manifest
fields, artifact verification, and the release-candidate gate.
